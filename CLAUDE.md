# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Що це

UkrFlow — голосовий диктант українською для macOS (аналог Wispr Flow), заточений під prompt engineering: користувач утримує гарячу клавішу (або вмикає hands-free і тапає), диктує (хоч 10–15 хв), текст локально розпізнається, шліфується LLM-кою і вставляється в активний застосунок. Клієнт (клавіші, мікрофон, словник, шліфування, вставлення, menu bar) — модуль `ukrflow.py`; розпізнавання — окремий спільний для всіх профілів macOS процес `ukrflow_server.py` (Whisper через MLX, лише `127.0.0.1`). Потрібен Apple Silicon (MLX).

## Команди

```bash
./run.sh                      # запуск (menu bar + глобальний слухач клавіш)
./run.sh --set-hotkey         # калібрування основної клавіші (натисканням)
./run.sh --set-hotkey clean   # окрема клавіша разового диктування в режимі
./run.sh --retry [--mode X]   # переобробити останній запис із recordings/
./install.sh                  # встановлення на новому Mac (venv + залежності)
./install-autostart.sh        # автозапуск при вході в систему (LaunchAgent)
./uninstall-autostart.sh      # вимкнути автозапуск і зупинити процес
.venv/bin/python bench_polish.py --dry-run   # бенчмарк шліфування: спершу лише план
```

`bench_polish.py` — ad-hoc інструмент, не частина застосунку: бере останні сирі тексти режимів `clean`/`prompt` з `ukrflow.log`, проганяє через матрицю бекенд × модель × effort тими самими функціями `POLISH_BACKENDS`, що й продакшен, і пише `runs/<дата>-bench-polish/REPORT.md` (`runs/` у `.gitignore`). **Кожен виклик — справжній `codex exec`/`claude -p` і витрачає квоту підписок**: спершу завжди `--dry-run`, стеля `--max-calls` (45), виклики строго послідовні. Без явного прохання користувача не запускати.

Автозапуск: LaunchAgent `com.ukrflow.app` викликає `.venv/bin/python ukrflow.py` **напряму** (не через `run.sh`) з `WorkingDirectory`. Проєкт **мусить лежати поза теками, захищеними TCC** (Desktop/Documents/Downloads): при вході в систему launchd/xpcproxy не може читати їх вміст — `posix_spawn` падає з «Operation not permitted» ще до старту Python, і жодні дозволи Python це не обходять (з термінала при цьому все працює — саме тому збій видно лише після перезавантаження). Тому проєкт фізично живе в `~/ukrflow`, а `~/Desktop/ukrflow` — симлінк для зручності; `install-autostart.sh` пише в plist фізичні шляхи (`pwd -P`) і відмовляється встановлюватись із захищеної теки. `KeepAlive.SuccessfulExit=false` — перезапуск після збою, але не після ручного Quit. Перед ручним `./run.sh` агент зупиняти (`./uninstall-autostart.sh` або `launchctl bootout`), інакше два екземпляри б'ються за клавіші й мікрофон; перезапуск після зміни коду: `launchctl kickstart -k gui/$(id -u)/com.ukrflow.app`. Сервер STT LaunchAgent-ом не керується: його піднімає клієнт, а виходить він сам за простоєм.

Меню в menu bar: «Режим» · «Бекенд» · «Hands-free (тап — старт, тап — стоп)» (перемикач `set_hands_free`, зберігається в конфіг, діє з наступного запису) · «Почати запис» (`("start-latched", …)` — hands-free запис одразу; push-to-talk, що вже йде, стає латчем) · «Зупинити запис» (`("stop", "меню", None)` — звичайний шлях зі збереженням, обробкою і вставленням) · «Скасувати запис» (`("cancel", …)` — без обробки й вставлення, WAV лишається, якщо запис ≥ `min_duration_sec`) · «Повторити останній запис» (`retry_last_recording()` — останній WAV із `recordings/` через сервер STT, без окремого процесу) · «Сервер STT…» (`/health` → notify: pid, user, модель, стан, простій) · «Зупинити сервер STT» (м'який `/shutdown`) · «Останній результат» · «Відкрити лог» · «Папка записів» · «Перезапустити UkrFlow» · «Вийти». Мережеві пункти меню працюють у daemon-потоці, результат — через notify. Перезапуск (`restart()`): під launchd (`XPC_SERVICE_NAME == com.ukrflow.app`) — `launchctl kickstart -k gui/<uid>/com.ukrflow.app` плюс страхувальний вихід із ненульовим кодом через 5 с (його підхопить `KeepAlive`), при ручному запуску — `os.execv`. Незавершене диктування перед перезапуском скидається в аварійний журнал і відновлюється після старту — окремої гілки збереження для перезапуску немає навмисно.

Тестового фреймворку немає — перевірки виконуються ad-hoc скриптами через `.venv/bin/python` (див. «Конвенції тестування» нижче). Синтаксис: `.venv/bin/python -c "import ast; ast.parse(open('ukrflow.py').read()); ast.parse(open('ukrflow_server.py').read())"`.

## Архітектура

### Пайплайн диктування

```
клієнт ukrflow.py:
  pynput (утримання / тап hands-free) → sounddevice 16 кГц → WAV у recordings/ (ДО обробки!)
  → SttClient: POST /transcribe на 127.0.0.1:<server_port> (тіло — WAV) → текст
       (сервер недоступний → stt_local_fallback: mlx_whisper у цьому процесі)
  → словник dictionary.json (точні заміни)
  → LLM-шліфування за активним режимом (codex / claude-code, fallback між ними)
  → буфер обміну + синтетичний Cmd+V
сервер ukrflow_server.py (один на всі профілі):
  mlx_whisper (language="uk", модель з локального кешу HF)
```

Заголовок блоку в `ukrflow.log`: `════ <час> ═ <wav> ═ аудіо X с, whisper Y с ═ режим: M (шліфування: P) ═ stt: pid N uid U[, старт Z с]` або `═ stt: локально`. `whisper Y с` — повний час розпізнавання разом із мережею й холодним стартом; `старт Z с` (`cold_start_sec`) — скільки з нього пішло на підняття сервера й завантаження моделі, щоб відрізняти повільний Whisper від холодного старту. Після шліфування — `── Відшліфовано (Z с, <backend>) ──` з текстом або `── Шліфування: без змін (<reason>[: <detail>]; Z с) ──`, де reason: `unchanged` (бекенд повернув той самий текст), `below_min` (коротше `polish_min_chars`), `off` (шліфування вимкнено або невідомий бекенд), `rejected` (`_validate_polish` відкинув відповідь: порожня або підозріла довжина), `failed` (збій CLI після повторів і fallback; у detail — однорядкова причина кожного бекенда). Без причини раніше збій і відкинутий результат у лозі не розрізнялись.

Ключові рішення, які легко зламати ненавмисно:

- **Аудіо зберігається на диск до будь-якої обробки** (`save_recording` у `_finalize_recording`) — це гарантія, що 15-хвилинне диктування не втрачається за жодного збою, зокрема коли сервер STT зник. Не переносити збереження пізніше по пайплайну.
- **Клієнт не імпортує `mlx_whisper` у штатному шляху** — лише ліниво в `transcribe_locally` (fallback), і модель після виклику одразу вивантажується (`ModelHolder.model = None`, `gc.collect()`, `mx.clear_cache()`). Глобальний імпорт чи кешування моделі в клієнті повернули б ~2 ГБ RAM у кожен профіль — саме від цього рятує сервер. `warmup()` модель більше не вантажить, лише друкує стан сервера.
- **Усі повтори розпізнавання — в одному циклі `SttClient.transcribe` з одним дедлайном** (`120 + 0.5×аудіо` с, на час `loading` — до `STT_LOADING_MAX_SEC`). `with_retries` навколо розпізнавання не повертати: вкладені повтори множили б мережеві таймаути до годин. Повтор лише для класу «сервер зник/закривається» (`SttGone`/`SttAbsent`/`SttClosing`); після read-timeout на тому самому pid запит не повторюється (чекаємо, поки self-watchdog сервера його вб'є); `500 mlx` — один м'який респавн на диктування; 400 — без повтору.
- **Cmd+V надсилається через Quartz за фізичним кодом клавіші** (`send_cmd_v`, keycode 9), а не символом — інакше ламається з активною українською розкладкою.
- **Синтетичний Cmd+V самого UkrFlow проходить через той самий event tap сесії**: `on_press`/`on_release` приймають прапорець `injected` від pynput і не рахують інжектовані події акордом — інакше вставлення попереднього диктування посеред утримання клавіші скасувало б наступне. Прапорець передає сам pynput 1.8 (`_handle_message` → `on_press(key, injected)`) — після оновлення pynput перевіряти разом із `_LISTENER_PATCHABLE`.
- **Без дозволу Accessibility** macOS мовчки ігнорує синтетичний Cmd+V; код перевіряє `AXIsProcessTrusted` і в такому разі лишає текст у буфері та не відновлює старий вміст.
- **Стопи «тиша» і «сесія» не вставляють** (`NO_PASTE_STOP_REASONS`): користувач, найімовірніше, не дивиться на екран, і Cmd+V полетів би в невідоме вікно, а відновлення буфера стерло б результат. Текст — у буфер обміну + `last.md` + notify «Текст у буфері — вставте Cmd+V»; так само, якщо в момент вставлення сесія вже неактивна (`_unpasted` → повторний notify, коли профіль повернеться). Стоп «вотчдог-латч» (фізичний тап, який зафіксував вотчдог) — це свідомий тап користувача, тож він **вставляє**, як і «hands-free», «release», «меню». Причина стопу йде `_finalize_recording → _process_safely → process_audio(paste_allowed=…)`.
- Збій шліфування (після retry і fallback-бекенда) → вставляється нешліфований текст. Диктування ніколи не блокується і не губиться.
- Кожен етап пишеться в `ukrflow.log` одразу (`log_block`), а не одним записом наприкінці.
- **Слухач клавіш — `ResilientListener`, а не голий `keyboard.Listener`**: pynput 1.8 не обробляє `kCGEventTapDisabledByTimeout/ByUserInput` (tap — локальна змінна в `ListenerMixin._run`, а саме повідомлення про вимкнення він видає за release), тож після вимкнення tap-а системою процес глухне до перезапуску. Підклас тримає посилання на tap, вмикає його назад і НЕ пускає цю подію далі в pynput; `_start_engine` перестворює слухач у циклі, а потік здоров'я додатково перевіряє `ensure_enabled()`. Ламається тихо — перевіряти після оновлення pynput (`_LISTENER_PATCHABLE`).
- **`stop_recording` не торкається потоку мікрофона** — лише перемикає стан і віддає роботу окремому потоку. Закриття CoreAudio-потоку (`_close_stream`) робиться в ще одному потоці з таймаутом `STREAM_CLOSE_TIMEOUT_SEC`, бо вміє не повернутися взагалі: саме так 🔴 висіла назавжди, а аудіо не доїжджало на диск. Чанки живуть у списку об'єкта `_Recording`, а не в полі застосунку, — недозакритий старий потік дописує у свій список, а не в наступне диктування. Оскільки відкриття і закриття тепер у різних потоках, їх серіалізує `_pa_lock` (PortAudio не потокобезпечний), а `sd._terminate()` при незакритому потоці не викликається взагалі — `Pa_Terminate` під ногами потоку, що сидить у `Pa_StopStream`, це segfault. Після зависання (`_pa_wedged`) наступні відкриття лока вже не чекають (його ніхто не відпустить) і користувач отримує одноразове сповіщення з порадою перезапустити застосунок.
- **Аварійний журнал** `recordings/*.pcm.part` (`RecordingJournal`): поки триває диктування, сирий PCM пишеться на диск щосекунди, а `recover_orphan_journals()` на старті (і в `--retry`) перетворює журнали мертвих процесів на звичайні WAV. Без нього аудіо жило лише в RAM і будь-який kill/перезапуск посеред 15-хвилинного диктування губив усе.
- **Вотчдог відпускання** (`_watch_release`) опитує фізичний стан клавіші двома джерелами (HID + сесія) і зупиняє запис лише після двох поспіль «відпущено»: подія release губиться при вимкненому tap-і, а із затиснутим лівим Cmd pynput бачить відпускання правого як press (він розрізняє модифікатори за спільним прапорцем). Виходить, щойно release свого `press_id` дійшов від слухача, і не стереже латч — інакше тап, що чекає латчу hands-free, зупинявся б як «загублений release».
- **Під launchd `Quartz.CGEventSourceKeyState` повертає 0** — за `launchd.log` «стан клавіші не читається» у 23 з 24 записів. Отже в продакшені `_watch_release`, `_watch_latch` і детектор «глухого tap-а» в `_watch_health` сліпі; кожен із вотчдогів пише про це одноразовий diag на запис («…стан клавіш(і) не читається — вотчдог неактивний для цього запису»). Ймовірна причина — Input Monitoring не надано саме `.venv/bin/python` (з термінала дозвіл має термінал); перевіряти в System Settings → Privacy & Security → Input Monitoring. Код мусить лишатися коректним і при завжди-нулі: тому `_watch_health` знімає застарілий `_hotkey_press` під час запису, лише якщо HID бачив клавішу натиснутою ПІСЛЯ цього press, а вотчдоги зупиняють запис лише після «бачив натиснутою → відпущено».
- **stdout line-buffered** (`main()`): під launchd stdout — файл, тож блочний буфер губить при вбивстві процесу саме той хвіст лога, де інцидент. Події життєвого циклу пишуться через `diag()`.

### Сервер STT (`ukrflow_server.py`)

Навіщо: користувач працює у двох профілях macOS (Fast User Switching), і кожен клієнт тримав власний Whisper large-v3-turbo (RSS ≈ 2 ГБ). Тепер модель живе в одному процесі на `127.0.0.1:<server_port>`, який піднімається на вимогу і сам виходить після простою; клієнти (~60–100 МБ) лишаються. Шліфування, словник, `prompts/` і конфіг — на клієнті кожного профілю (своя підписка). Сервер самодостатній: лише stdlib на верхньому рівні (bind і `/health` відповідають за частки секунди), `numpy`/`mlx_whisper` імпортуються ліниво в потоці завантаження; `ukrflow.py`, pynput, rumps, Quartz він не імпортує.

Протокол (JSON, `Connection: close`, лише `http.client` на `127.0.0.1` — не urllib, бо системні проксі `_scproxy`, і не `localhost`, бо `::1`):
- `GET /health` → `app: "ukrflow-stt"`, `proto`, `version`, `pid`, `uid`, `user`, `model_state ∈ {idle, loading, ready, error}`, `model`, `busy`, `idle_sec`, `draining`, `last_error`, `log_path`…; не бере `_gpu_lock` і не оновлює простій; у `draining` → 503.
- `POST /touch` — keepalive; `POST /warm` (meta `model`, `language`) → 202, завантаження у фоні; `POST /transcribe` (meta `model`, `language`, `initial_prompt`, `audio_sec`, тіло — WAV, `Content-Length` обов'язковий → інакше 411, > 64 МіБ → 413); `POST /shutdown` — м'який (чекає `busy == 0` до 30 с), `force` приймається лише від того самого uid.
- Кожен POST вимагає `X-UkrFlow-Proto` (інша версія → 409) і `X-UkrFlow-Uid`; параметри — лише в `X-UkrFlow-Meta: base64url(JSON)` (кирилиця `initial_prompt` у заголовку `http.client` падає на latin-1). Запит з `Origin` або з `Host ≠ 127.0.0.1:<port>` → 403, `OPTIONS` → 405 — захист від браузерних no-cors POST на loopback. `model` — лише HF repo id: локальний шлях із чужого `$HOME` іншому профілю недоступний.
- Помилки типізовані полем `kind`: 400 `bad_audio`/`bad_meta` (не повторювати), 503 `loading` (чекати) / `closing` (дочекатись виходу й підняти новий), 500 `mlx` (допомагає респавн). Клієнт на цьому будує класи `SttAbsent`, `SttGone`, `SttBusy`, `SttClosing`, `SttLoading`, `SttForeign`, `SttProtoMismatch`, `SttMlxError`, `SttDeadline`.
- Коди виходу: 0 — ідл-вихід / `/shutdown` / SIGTERM; 3 — порт зайнятий (`EADDRINUSE`, програв арбітраж); 1 — self-watchdog або фатальна помилка (зокрема ввімкнений `SO_REUSEPORT`).

Життєвий цикл:
- **Спавн клієнтом при підтвердженні запису** (`_warm_stt` з `_confirm_recording` або `_latch`, один раз на `_Recording`): `warm_async` → `ensure_server()` + `/warm`, тож модель вантажиться паралельно з мовленням і на стоп уже готова. Тапи сервер не будять. `keepalive` шле `/touch` кожні `STT_KEEPALIVE_SEC` (15 с) до `rec.stop_event`; якщо сервер не відповідає — `ensure_server` + `/warm`, щоб сервер, що впав посеред диктування, встиг прогрітись до стопу.
- `ensure_server` — double-checked під `_spawn_lock` (прогрів, keepalive і розпізнавання можуть одночасно побачити refused); `Popen([sys.executable, ukrflow_server.py, --port, --idle-sec, --log server.log])` з `start_new_session=True` (переживає перезапуск клієнта), env без `XPC_*` (інакше сервер виглядав би частиною служби `com.ukrflow.app`), stderr — у `server.log`; потік-реапер `proc.wait()` (інакше після ідл-виходу — зомбі). Опитування `/health` кожні 0.2 с до `server_ready_timeout_sec` (лише HTTP-готовність). Код 3 → ще 3 с чекати чужий сервер, далі один повторний спавн через 1 с (TIME_WAIT, вмираючий сервер); інший код → негайна помилка з хвостом `server.log` у консоль і одноразовий notify (зламаний venv, ImportError).
- **EADDRINUSE-арбітраж між профілями**: перший, хто зробив bind, і є сервер; другий виходить кодом 3, і обидва клієнти бачать один `/health`. `allow_reuse_address=True` лишити (після kill/logout порт у TIME_WAIT), `SO_REUSEPORT` — ніколи (з ним «переможців» двоє). `server.log` відкривається й ротується лише переможцем.
- **Ідл-вихід** (крок 1 с): `busy == 0`, модель не `loading` і простій > `server_idle_sec` → `draining` (усі нові запити — 503 `closing`) → закрити слухаючий сокет → `os._exit(0)`. Без draining була б гонка «`/health` відповів OK, а за мить процес зник».
- **Self-watchdog без GIL**: `faulthandler.dump_traceback_later(exit=True)` навколо кожної GPU-операції (`60 + 0.5×audio_sec` для розпізнавання, 900 с для прогріву). Це єдиний спосіб звільнити порт, коли завислий у MLX процес належить іншому uid. Усі виклики `mlx_whisper` — під одним `_gpu_lock` (`ModelHolder` не потокобезпечний); модель вантажиться з `snapshot_download(local_files_only=True)`, мережа до HF — лише при першому завантаженні.
- **Несумісний `proto`** (профілі на різних комітах): клієнт пише diag «оновіть клон у профілі X»; якщо чужий сервер простоює — м'який `/shutdown` з ЙОГО версією протоколу (інакше він відповів би 409) → дочекатись закриття порту → спавн свого; якщо зайнятий — 10 с очікування, далі збій і локальний fallback.
- **Чужий процес на порту** (`app ≠ ukrflow-stt`, не HTTP) → `SttForeign` з підказкою змінити `server_port`; спавнити поверх нього марно. Порт мусить бути однаковим в усіх профілях, інакше кожен підніме свій сервер.
- **`stt_local_fallback`** (true): дедлайн вичерпано або сервер недоступний (чужий завислий процес, зламаний venv, зайнятий несумісний сервер) → `transcribe_locally` + diag + одноразовий notify. Диктування не губиться ніколи; false — `SttError` іде в `_process_safely` (⚠️ + «Повторити останній запис»).
- `server.log` живе в клоні того профілю, чий клієнт спавнив сервер (`--log` — шлях його клону); при > 5 МБ на старті переїжджає в `server.log.1`. `log_message` мовчить для `/health` і `/touch`; на `/transcribe` — один рядок (uid, тривалість аудіо, секунди, без тексту), плюс старт/модель/причина виходу/traceback.

Ключі конфігу: `server_port` (47117), `server_idle_sec` (60), `server_ready_timeout_sec` (10), `stt_local_fallback` (true).

Що легко зламати / що перевіряти вручну:
- **Metal/MLX із фонової сесії Fast User Switching** не перевірено: якщо власник сервера у фоні, а диктують з іншого профілю, RTF у `ukrflow.log` (`whisper Y с` проти `аудіо X с` + `stt: … uid U`) має лишатись нормальним. Запасний план — окремий сервер на профіль або LaunchDaemon із socket activation.
- **Поведінка після `launchctl kickstart -k` клієнта і після logout власника**: сервер у власній сесії й очікувано живе до ідлу; якщо launchd вбиває його разом зі службою — клієнт просто підніме новий, але перевіряти `pgrep -U <uid> -f ukrflow_server` після kickstart. Запасний план — on-demand LaunchAgent `com.ukrflow.stt`.
- Сервер ніколи не вбивати зі скриптів (`install-autostart.sh`, `uninstall-autostart.sh`): він може обслуговувати інший профіль просто зараз; несумісну версію замінює `proto`, решту — ідл-вихід. `pgrep`/`pkill` у скриптах — лише з `-U "$(id -u)"`, інакше вони бачать процеси іншого профілю.
- Зміна протоколу (нові поля meta, інша семантика відповіді) → підняти `PROTO` у сервері і `STT_PROTO` у клієнті разом.

### Два профілі

Кожен профіль має свій клон `/Users/<user>/ukrflow` зі своїм `.venv`, кешем моделі, `config.json`, `prompts/` і LaunchAgent `com.ukrflow.app`; сервер STT — один на обидва. Після змін **оновлювати обидва клони** (з відповідного профілю): `git pull`, `.venv/bin/pip install -r requirements.txt`, `launchctl kickstart -k gui/$(id -u)/com.ukrflow.app`. Якщо один клон відстав і протокол змінився — це лікується автоматично (м'який `/shutdown` + свій сервер), але в лозі буде diag «оновіть клон у профілі X». Логи сервера шукати в клоні того профілю, що його підняв (`/health` → `log_path`, меню «Сервер STT…» → user).

### Hands-free

Перемикач у меню (`config["hands_free"]`, false за замовчуванням), діє з наступного запису (`_Recording.hands_free` — знімок на старті). З вимкненим hands-free поведінка стара: утримання — push-to-talk, тап тихий, подвійний тап основної клавіші — `cycle`.

З увімкненим:
- **Чистий тап** основної клавіші (press→release ≤ `tap_max_sec`, без інших клавіш) → `latch_pending`; якщо за `double_tap_gap_sec` після відпускання не було нового натискання — латч: ⏺ в іконці, звук `SOUND_LATCH` (Hero, відмінний від push-to-talk), прогрів сервера, латч-вотчдог, таймер тиші. Без notify.
- Друге натискання у вікні латчу: коротке → подвійний тап (запис скасовано без WAV + `cycle`); довге → push-to-talk-стоп з аудіо від першого натискання.
- Утримання > `tap_max_sec` — push-to-talk в обох режимах.
- Клавіші режимів: тап → латч одразу (подвійного тапу в них немає); так само для основної клавіші при `mode_cycle_double_tap: false`.
- Під час латчу **чистий тап будь-якої гарячої клавіші** → стоп «hands-free», і ще `double_tap_gap_sec` тапи ігноруються (подвійний тап «за звичкою» → тихе скасування без WAV, а не новий латч). Акорд під час латчу (Cmd+Tab, Cmd+C) запис не зупиняє.
- Акорд під час НЕлатченого запису → скасування «акорд» (тихо, WAV зберігається).
- **Автостоп тиші** `hands_free_silence_stop_sec` (120; 0 — вимкнено): лише для латчу, RMS останніх N с < `silence_rms_threshold` → стоп «тиша» без вставлення. Це захист від забутого латчу, а **не ліміт тривалості** — поки звучить мова, запис не обривається; жорсткого ліміту в проєкті немає.

Ключові рішення машини станів (легко зламати ненавмисно):
- **Потік слухача нічого не вирішує**: `on_press`/`on_release` лише нумерують натискання монотонним `press_id`, ставлять мітки часу (`_press_info`, `_released`, `_chord`) і кладуть `("press"|"release", key, press_id, t)` у чергу. Повторний keyDown клавіші, що вже в `_hotkey_press` (автоповтор f13/vk, press замість release у модифікаторів), ігнорується. Будь-яка не-інжектована клавіша, поки гаряча натиснута, — `chord[press_id] = True`.
- **Рішення лише у воркері** (`_recorder_worker` → `_on_hotkey_press`/`_on_hotkey_release`/`_on_confirm`/`_on_latch_timer`), за мітками часу слухача, а не воркера: `_open_stream` буває > 1 с, і за часом воркера тап виглядав би утриманням.
- **Таймери лише кладуть команди в чергу** (`("confirm", gen, press_id)`, `("latch", gen, tap_seq)`); воркер перевіряє покоління запису, `press_id`/`tap_seq` і що після тапу не було нового press — застарілий таймер є no-op.
- `_watch_release` виходить, щойно release його `press_id` є в `_released`; латч стереже `_watch_latch`: фізичний down→up гарячої клавіші без пари press/release від слухача за `LATCH_WATCH_GRACE_SEC` (0.4 с) → стоп «вотчдог-латч» (вставляє), `listener.stop()` (як при «глухому tap-і») і notify. Під launchd він сліпий — див. вище.
- **Скасовані записи** (`cancel_recording`: акорд, меню «Скасувати запис») зберігають WAV при тривалості ≥ `min_duration_sec` — голос, наговорений до випадково зачепленої клавіші, підбере «Повторити останній запис»; подвійний тап і тап без hands-free скасовуються з `keep_audio=False`, щоб їхній WAV не підмінив справжнє останнє диктування. Порядок при подвійному тапі: спершу скасування, потім `cycle` (`set_mode` має бачити `recording=False`).
- Release натискання, що почалося до латчу (меню «Почати запис» посеред утримання), стопом не є — стоп лише для `rec.stop_candidate`.
- `_finalize_recording`: `was_tap = duration ≤ tap_max_sec and not latched` — стоп латчу завжди чутно.

### Режими

`config["modes"]` — словники, що перекривають базовий конфіг на час одного диктування через `effective_config()`. Кожен режим = файл інструкції в `prompts/*.md` (перечитується перед кожним викликом — редагується наживо) + довільні перекриття (`polish`, модель, effort). Липкий режим — `config["mode"]`; перемикається з меню в menu bar, подвійним тапом основної клавіші (цикл за порядком у словнику) або разовими клавішами режимів (`mode["hotkey"]`).

Стандартні режими: `raw` (polish off), `clean` (виправлення без переробки), `prompt` (prompt engineering, типовий).

### Бекенди шліфування (`POLISH_BACKENDS`)

Лишилось два; `local` (Qwen через mlx-lm) і `api` (anthropic SDK) вилучено. `load_config()` мігрує старий конфіг: прибирає `polish_local_model`/`polish_api_model` (і з режимів), а `polish: "local"|"api"` перемикає на `codex`.

- `codex` (типовий) — subprocess `codex exec` з підпискою ChatGPT. Виклик ізольований через `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--sandbox read-only` та порожню тимчасову теку; інструкція — позиційним аргументом, розшифровка — stdin; фінальна відповідь читається з `--output-last-message`.
- `claude-code` — subprocess `claude -p` з підпискою користувача; інструкція — `--system-prompt`, розшифровка — stdin. Критичні прапорці: `--no-session-persistence` (користувач принципово не хоче сміттєвих сесій), `--effort low` (без нього виклик ~60 с замість 3–10 с), `--strict-mcp-config` з порожнім набором (інакше вантажаться MCP-сервери користувача), `--safe-mode` (вимикає хуки, плагіни, skills і CLAUDE.md з `~/.claude` — без нього вони просочувались у відповідь: у логах модель двічі ВІДПОВІЛА на диктування замість переписати), `--tools ""` (жодних інструментів), `--disable-slash-commands`, cwd — порожня тимчасова тека. `--bare` не використовувати — він пропускає OAuth, тобто підписку.

Базовий бекенд — `config["polish"]`; він перемикається наживо через підменю «Бекенд» і діє з наступного диктування. Режим може перекривати його (стандартний `raw` завжди задає `polish: off`). `polish_fallback` (`"auto"` — протилежний із пари codex/claude-code, `"off"`, або назва бекенда): після невдачі основного (звичайні збої — після `retries`) пробується fallback. Ліміт підписки (`usage limit`, `you've hit`, `at capacity`, `rate limit`, 429… — шукається лише в хвості stderr/stdout, не в промпті) і відкинутий `_validate_polish` результат **не повторюються** (`PolishQuotaError`/`PolishRejected`) — одразу fallback, при ліміті — notify. У логах усі остаточні збої були саме «usage limit», і повтори через 2 с нічого не давали.

### Потоки

Головний потік — rumps (GUI menu bar); слухач pynput і `_start_engine` — фоновий потік; кожне диктування обробляється в daemon-воркері (`_process_safely` — обгортка, що перетворює будь-який виняток на ⚠️ + сповіщення + підказку «Повторити останній запис»). Усю машину станів клавіш, старт/стоп/скасування/латч і команди меню серіалізує `_recorder_worker` (callback слухача мусить повертатися миттєво), фіналізацію і закриття мікрофона — окремі потоки, аварійний журнал — свій потік. На кожен підтверджений запис — потоки `warm_async` і `keepalive` сервера STT, на латч — `_watch_latch` і `_watch_silence`; кожен спавнений сервер має потік-реапер. `_watch_health` (крок `HEALTH_POLL_SEC`) вмикає назад вимкнений event-tap, перезапускає слухач, якщо клавіша фізично натиснута ≥ `DEAF_TAP_HOLD_SEC`, а подій немає («глухий tap»), і сповіщає про воркер, що завис довше за `WORKER_STUCK_SEC`. `_watch_session` при переході профілю у фон кладе стоп «сесія». Будь-які оновлення GUI (титул іконки, галочки меню) — лише через `NSOperationQueue.mainQueue()`. `StatusIndicator` без прикріпленого GUI — no-op (так працюють `--retry` і тести).

### Подвійний тап і відкладений фідбек

Тап = натискання коротше `tap_max_sec` (0.35 с). Аудіопотік стартує з першої мілісекунди натискання, але звук початку і 🔴 з'являються лише після порогу тапу (таймер `confirm` → `_on_confirm` → `_confirm_recording`, відлік від мітки натискання слухача) — тому тапи тихі й не миготять іконкою, і сервер STT вони не будять. Тап відкидається за мітками слухача, а не за довжиною аудіо: поки наступне відкриття мікрофона тримає `_pa_lock`, потік тапу ще дописує чанки. Не повертати «миттєвий» фідбек: це свідоме UX-рішення.

## Конвенції

- **Усе українською**: коментарі, повідомлення в консоль, документація. Виняток — назви пунктів меню macOS в інструкціях для користувача пишуться англійською (System Settings → Privacy & Security), бо macOS користувача англомовна.
- **Жодного хардкоду словників/термінів**: `dictionary.json` та `initial_prompt` порожні/нейтральні за замовчуванням — їх наповнює користувач. Інструкції LLM живуть у `prompts/*.md` як дані, а не в коді (`DEFAULT_PROMPTS` у коді — нейтральні).
- `load_config()` мерджить `DEFAULT_CONFIG` з `config.json` і записує результат назад — нові ключі з'являються у файлі автоматично. `config.json` — живий стан користувача (поточний режим, клавіші, hands-free): не перезаписувати його значення дефолтами; вилучені ключі мігрувати явно.
- Диктування на 10–15 хвилин — норма: не додавати часових лімітів (таймаути `codex`/`claude` CLI — 600 с; дедлайн розпізнавання росте з тривалістю аудіо). `hands_free_silence_stop_sec` — не ліміт, а захист від забутого латчу.
- `requirements.txt` — один venv на клієнт і сервер; `mlx-lm` і `anthropic` вилучено разом із бекендами.

## Конвенції тестування

- Перевірки — інлайн-скрипти через `.venv/bin/python` з підміною важких/побічних частин: `ukrflow.sd.InputStream` → заглушка, `ukrflow.play_sound` → колектор, `app.paste` → заглушка (**ніколи не викликати справжній `paste` у тестах** — він перезапише буфер обміну користувача і натисне Cmd+V в активному вікні).
- Підміняти `ukrflow.RECORDINGS_DIR` (а також `LAST_PATH`, `LOG_PATH`, `CONFIG_PATH`, `DICTIONARY_PATH`, `SERVER_LOG_PATH`) на тимчасову теку, а конфіг брати як `dict(DEFAULT_CONFIG)`: `load_config()` пише у файл користувача, а тестові WAV і `*.pcm.part` у `recordings/` збили б `--retry` і відновлення журналів.
- Не лишати тестові WAV у `recordings/` (`--retry` бере останній файл) і не змінювати `config["mode"]`/`config["hands_free"]` користувача — підміняти `set_mode`/`save_config` або чистити за собою.
- **Застосунок користувача зазвичай працює** (LaunchAgent, можливо і в другому профілі): не запускати `./run.sh`, не перезапускати агент, не займати мікрофон і не створювати справжній слухач клавіш у тестах.
- **Серверні тести — лише на випадкових вільних портах** (`ukrflow_server.py --port <вільний> --idle-sec 3 --log <тимчасова тека>`), ніколи на `server_port` користувача (47117): там може жити сервер, яким саме зараз користується інший профіль.
- **Клієнт — з фейковим сервером** (in-process `http.server` на випадковому порту, `config["server_port"]` на нього, `SttClient._spawn` підмінено): refused → спавн, 503 `closing`/`loading`, read-timeout, 500 `mlx`, 409, чужий `app`, дедлайн → `stt_local_fallback` (`transcribe_locally` підмінено).
- **Жодних реальних викликів `codex`/`claude` у тестах** — вони витрачають квоту підписок: підміняти `POLISH_BACKENDS`/функції бекендів або `subprocess.run`. Справжні виклики — лише `bench_polish.py` за проханням користувача.
